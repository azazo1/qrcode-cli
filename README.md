# qrcode

二维码编解码命令行工具. 可以从管道, 系统剪贴板或命令行参数读取图片并解码,
也可以把文本编码成二维码在终端或浏览器里显示.

解码基于纯 Go 的 [gozxing](https://github.com/makiuchi-d/gozxing) (ZXing 的移植),
构建产物是单文件二进制, 运行时不需要安装任何额外软件.

## 安装

从 [Releases](https://github.com/azazo1/qrcode-cli/releases) 下载对应平台的归档,
解压后把 `qr` 放到 `PATH` 里即可. 产物是静态链接的单文件二进制, 不需要 Go 环境,
也不需要 OpenCV 之类的系统库.

需要自己构建时, 要求 Go 1.27 或更高版本:

```shell
just build
```

这样的开发构建版本号显示 `dev-build`, 不携带 git 信息.

## 版本号

`--version` 显示的版本号由构建时的 git 状态决定:

| 构建状态 | 显示 |
|---|---|
| 恰好在一个版本 tag 上 | `v0.1.0` |
| 版本 tag 之后的提交 | `v0.1.0-a1b2c3d` |
| 工作区有未提交改动 | `v0.1.0^a1b2c3d` |
| 日常开发构建 | `dev-build` |

发布产物由 `just dist` 生成, 归档名里的版本段不带 `v` 前缀, 例如
`qr-0.1.0-linux-x86_64.tar.gz`.

## 选项

```
qr -h              查看完整帮助
qr --version       查看版本
```

| 选项 | 适用 | 说明 |
|---|---|---|
| `-i, --input` | 通用 | 输入来源: `-` 表示标准输入, `clipboard` 表示剪贴板, 其他值按路径处理 |
| `-o, --output` | 通用 | 输出路径; 扩展名为 `.txt` 时输出字符画, 其他按 PNG |
| `-v, --verbose` | 通用 | 输出更详细的调试日志到 stderr |
| `--json` | 解码 | 输出结构化结果 |
| `--text` | 解码 | 只输出二维码内容, 每行一条 |
| `--no-preprocess` | 解码 | 关闭放大与反色等预处理 |
| `-l, --level` | 编码 | 纠错等级 `L` `M` `Q` `H`, 默认 `M` |
| `-s, --size` | 编码 | PNG 每模块像素数, 默认 8 |
| `--terminal` | 编码 | 标准输出不是终端时也打印字符画 |
| `--web` | 编码 | 强制用浏览器显示 |
| `--no-open` | 编码 | 启动网页服务后不自动打开浏览器 |
| `--port` / `--bind` | 编码 | 网页服务的端口与监听地址 |
| `--no-color` | 编码 | 字符画不带 ANSI 配色 |

退出码: `0` 成功, `1` 用法或 IO 错误, `2` 没有找到二维码, `130` 被 Ctrl+C 中断.

## 日志

每次调用都会往 stderr 打一行, 说明读了什么, 按什么模式处理, 结果写到哪里:

```
time=23:28:51 level=info msg=输入源与模式 mode=encode by=auto origin=arg \
  source=参数 kind=文本 content="https://example.com" bytes=19 output=stdout(chars)
```

各字段含义:

| 字段 | 说明 |
|---|---|
| `mode` | `decode` 或 `encode` |
| `by` | `auto` 表示由程序按输入内容判定, `explicit` 表示写了 `d`/`e` 子命令 |
| `origin` | `arg` 参数, `file` 文件, `stdin` 管道, `clipboard` 剪贴板 |
| `source` | 具体名称, 例如文件名或 "剪贴板图片" |
| `kind` | `图片` 或 `文本` |
| `content` | 读到的东西本身: 文本输入显示文本内容, 图片输入显示格式 |
| `bytes` | 输入字节数 |
| `output` | 结果去向, 例如 `stdout(png)`, `stdout(chars)`, `file:x.png`, `web` |

`content` 让日志直接告诉你读到了什么, 而不只是一个来源名称. 文本超过 120 字符时
截断并注明原始长度. 含空格, 等号或换行的值会加引号, 保证相邻字段仍能区分.

在终端里 `content` 显示为浅灰色, 与 `mode`, `origin`, `output` 这些判断依据区分开.
日志被重定向到文件或管道时不加颜色; 设置 `NO_COLOR` 环境变量也能关闭颜色.

`output` 为 `web` 时端口由系统分配, 真实地址在服务启动后单独记一行.

多文件解码时, 每个来源各记一行. 被跳过的输入会额外记一条 `warn`, 避免用户
困惑某个输入为什么没有产生结果.

日志只写 stderr, 因此不会污染 stdout 上的二维码内容或 PNG 二进制, 管道用法不受影响.

加 `-v` 后还会输出每个阶段的耗时, 识别到的二维码位置与纠错等级等细节.

## 用法

### 编码

```shell
# 在终端显示二维码
qr e "https://example.com"

# 输出 PNG 文件
qr e "https://example.com" > example.png

# 指定纠错等级与模块像素大小
qr e "https://example.com" -l H -s 10 -o example.png

# 文本太长, 终端放不下时自动改用浏览器显示
qr e "$(cat long-text.txt)"
```

标准输出是终端时打印字符画; 是管道或文件时输出 PNG 二进制. 想强制字符画可以用
`--terminal`.

### 解码

```shell
# 解码图片文件
qr d shot.png

# 从管道解码
cat shot.png | qr

# 复制截图后直接运行, 自动读取剪贴板图片
qr

# 一张图里有多个二维码, 全部列出
qr d multi.png
```

一张图里有多个二维码时, 按阅读顺序 (从上到下, 从左到右) 编号输出:

```
[1] https://first.example
[2] second-qr-code
[3] third-内容
```

需要机器处理时用 `--json`:

```shell
qr d multi.png --json
```

### 自动模式

不带子命令时按输入内容判定:

| 输入 | 结果 |
|---|---|
| 参数是图片文件 | 解码 |
| 参数是其他文件 | 按文件内容编码 |
| 参数不是文件 | 按文本编码 (多个参数用空格拼接) |
| 标准输入是管道且内容是图片 | 解码 |
| 标准输入是管道且内容是文本 | 编码 |
| 标准输入读不到任何数据 | 继续尝试剪贴板 |
| 无参数且没有管道数据 | 优先读剪贴板图片解码, 否则读剪贴板文本编码 |

在脚本里建议显式写 `d` 或 `e`, 行为更可预测.

从管道, 文件或剪贴板取到的文本会去掉末尾的单个换行: `echo hello | qr` 编码的是
`hello` 而不是 `hello` 加换行. 确实需要编码换行时, 把文本作为命令行参数传入即可,
显式参数保持原样.

还需要注意, 显式解码 (`qr d`) 的输入必须是图片. 文件不存在, 内容不是图片,
或者剪贴板里只有文本, 都会直接报错, 而不是退化成 "没有找到二维码".

## 终端显示

一个终端字符格子的宽高比约为 1:2, 因此竖直方向的两个模块合并进一个字符,
用 `█`, `▀`, `▄` 和空格四种字符表示. 这样显示出的二维码接近正方形,
占用行数只有模块数的一半.

二维码放不进当前终端, 或者加了 `--web` 时, 会启动一个本地网页服务:

```
二维码完整显示在 http://127.0.0.1:53219/
按 Ctrl+C 结束服务
```

服务只监听回环地址, 页面可以反复刷新, 按 Ctrl+C 退出. 端口可以用 `--port` 固定.

二维码放不下时会用系统默认浏览器自动打开该页面. 不希望被打断时加 `--no-open`,
程序只打印地址并继续等待. 自动打开失败 (例如没有可用的浏览器) 只会打印一条提示,
服务照常运行.

如果显式用 `--bind` 监听到非回环地址, 程序会提示二维码内容对内网可见.

## 剪贴板

剪贴板读取基于 [golang.design/x/clipboard](https://pkg.go.dev/golang.design/x/clipboard).
该库通过 `purego` 动态加载系统库, 桌面平台上**不需要 cgo**, 也**不需要**任何
外部命令:

| 平台 | 运行方式 | 额外依赖 |
|---|---|---|
| macOS | 直接调用 AppKit 的 NSPasteboard | 无 |
| Windows | 直接调用 Win32 剪贴板接口 | 无 |
| Linux (Wayland) | 通过 Wayland 的 data-control 协议 | 需要合成器支持该协议 |
| Linux (X11) | 直接使用 X11 协议 | 需要 X server |

Linux 上库会自动判断用 Wayland 还是 X11. 老版本 Wayland 合成器若不提供
data-control 协议, 会退回到 XWayland, 因此需要 X server 可用.

在没有图形界面的环境 (例如纯命令行服务器) 里, 读剪贴板会返回明确的不支持
错误, 而不是崩溃.

一次剪贴板读取是微秒级的函数调用, 而不是启动子进程, 所以不需要担心开销.

## 关于识别能力

解码器使用 ZXing 的算法, 分两轮尝试不同图像变体.

第一轮是低代价的常规变体, 覆盖绝大多数场景:

- 深色背景浅色二维码: 反色后重新识别
- 小尺寸图片: 短边不足 512 像素时整数倍放大
- 超大图片: 长边超过 3000 像素时先等比缩小, 控制耗时

第二轮是增强变体, 代价明显更高:

- 转灰度, 只按亮度二值化, 避免彩色噪点干扰
- 对比度拉伸: 用 2% 与 98% 分位点把亮度拉回全量程, 救回浅灰底深灰码这类低对比度图片
- 3x3 中值滤波: 去掉椒盐噪点与压缩伪影留下的孤立像素, 同时保住二维码的方块边缘

增强变体**总是**执行, 不会因为常规变体已经找到二维码就跳过. 原因是一张图里
多个二维码的质量可能不一致: 清晰的那几个被常规变体识别出来之后, 有噪声或
低对比度的那一个就只能靠增强变体. 提前跳过会让工具少报一个码, 而且没有任何
提示, 这比慢几十毫秒糟糕得多.

去噪必须在放大之前完成. 最近邻放大会把单个噪点复制成 2x2 的块, 3x3 中值滤波
无法清除这种块, 顺序颠倒就会让去噪完全失效.

实测表现 (400 像素见方的二维码):

| 场景 | 未增强 | 增强后 |
|---|---|---|
| 撒 3000 个随机彩色噪点 (1.9% 像素) | 失败 | 成功 |
| 前景亮度 130 / 背景 200 的低对比度 | 失败 | 成功 |
| 任意角度旋转 (15, 30, 45, 137, 180, 270 度) | 成功 | 成功 |
| 3x3 模糊 | 成功 | 成功 |
| 纠错等级 M 下中心遮挡 20% 边长 | 成功 | 成功 |
| 纠错等级 M 下中心遮挡 25% 边长 | 失败 | 失败 |

最后一行是固有边界: 遮挡再大就会破坏二维码的对齐图案, 采样网格无法建立.

耗时参考 (本机 arm64):

| 输入 | 耗时 |
|---|---|
| 单码 400x400 | 约 30 ms |
| 三码 1200x400 | 约 85 ms |
| 2560x1440 屏幕截图 | 约 160 ms |
| 25 个码的 1500x1500 拼图 | 约 500 ms |

需要更快时可以用 `--no-preprocess` 关闭全部预处理与增强, 只做最原始的单次识别,
代价是会失去上表中所有"增强后"的能力.

微信开源的 OpenCV `wechat_qrcode` 引擎 (CNN 检测 + 超分辨率) 在严重模糊, 强透视,
极小尺寸的照片上表现更好. 但它需要 OpenCV 动态库与模型文件, 无法做成可移植的
单文件二进制, 因此这里选择了零依赖的路线. 解码器在 `internal/decode` 中抽象成了
接口, 将来接入其他引擎不需要改动调用方.

```shell
just          # 列出所有 recipe

just run -h   # 直接运行
just test     # 运行测试
```
